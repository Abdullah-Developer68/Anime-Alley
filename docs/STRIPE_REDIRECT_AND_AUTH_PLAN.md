## 1. Executive Summary & Root Cause Analysis

### 1.1 The Bug
When a user completes a Stripe payment, instead of viewing their order confirmation and being smoothly transitioned to their order history, the user gets stuck on the `/login` screen and appears completely logged out.

### 1.2 Root Cause Breakdown

#### Primary Cause: Cross-Origin Redirect Mismatch & Same-Origin Policy
1. **Origin Isolation in `localStorage`**:
   The user tests or operates the application on their Vercel preview branch deployment:
   `https://anime-alley-client-git-main-developers-projects-86df454e.vercel.app`
   Authentication credentials (`authToken` and `userInfo`) are persisted in browser `localStorage`. Under the W3C Web Same-Origin Policy (RFC 6454), `localStorage` is strictly partitioned per origin (`protocol + domain + port`). Data stored under one origin is completely inaccessible to any other origin.

2. **Hardcoded Redirect Target in Stripe Session**:
   In `server/services/stripe.js` (lines 103–104), checkout redirect URLs are hardcoded to the backend environment variable:
   ```javascript
   success_url: `${process.env.CLIENT_URL}/success?session_id={CHECKOUT_SESSION_ID}`,
   cancel_url: `${process.env.CLIENT_URL}/cart`,
   ```
   On Vercel, `process.env.CLIENT_URL` is set to the primary production alias:
   `https://anime-alley-beige.vercel.app`

3. **Origin Jump upon Payment Completion**:
   When payment succeeds, Stripe redirects the browser to:
   `https://anime-alley-beige.vercel.app/success?session_id=cs_test_...`
   The browser switches origins. On `anime-alley-beige.vercel.app`, `localStorage.getItem("authToken")` and `localStorage.getItem("userInfo")` are both `null` because the user never logged in on this domain.

4. **API 401 Cascade & Storage Purge**:
   - On `/success`, `Success.jsx` calls `api.verifyOrder(session_id)`.
   - Because `authToken` is `null`, Axios sends the request without an `Authorization: Bearer <token>` header.
   - In `server/routes/modules/order.route.js`, line 18 enforces `router.use(verifyTokenMiddleware)` across **all** order routes, including `/verifyOrder`.
   - The server rejects the request with `401 Unauthorized` (`"Authentication failed. No token provided"`).
   - In `client/src/api/api.js` (lines 37–40), the Axios response interceptor intercepts the 401 and calls `clearAllUserData()`, purging whatever storage existed.

5. **Route Guard Ejection to `/login`**:
   - Even when the order is recorded by the Stripe webhook, `Success.jsx` calls `navigate("/history")`.
   - The `/history` route is wrapped in `<ProtectedRoute>` (`client/src/components/ProtectedRoute.jsx`).
   - In `ProtectedRoute`:
     ```javascript
     if (!user) {
       return <Navigate to="/login" state={{ from: location }} replace />;
     }
     ```
   - Because `user` is `null` on `anime-alley-beige.vercel.app`, the user is ejected to `https://anime-alley-beige.vercel.app/login` with no session.

#### Secondary Discovered Defects
1. **Typo in `userSessionManager.js` (`"token"` vs `"authToken"`)**:
   In `client/src/utils/userSessionManager.js` (line 21), `itemsToPreserve` lists `"token"` instead of the actual key `"authToken"`. If `clearUserData()` is invoked on user state updates, it unintentionally purges the active auth token.
2. **Missing Polling Interval Cleanup in `Success.jsx`**:
   In `client/src/pages/Success.jsx`, `useEffect` establishes `setInterval` without returning a cleanup function (`clearInterval(timer)`). If the user navigates away or unmounts the component, the timer leaks in memory and continues polling.
3. **Unnecessary Authentication Barrier on `/verifyOrder`**:
   `api.verifyOrder` only takes `stripeSessionID` (a cryptographically random token with 256-bit entropy generated by Stripe) to check whether the order has synced into MongoDB. It does not access `req.user` or expose sensitive user records. Forcing it behind `verifyTokenMiddleware` creates unnecessary failure points during post-payment redirect transitions.

## 2. Opus 4.6 Tier Architectural & Security Audit

The architecture was evaluated against Opus 4.6 tier standards and verified through independent architectural review. Below are the key findings and hardening measures integrated into this plan:

### 2.1 Open Redirect & Header Spoofing Audit
* **Risk:** Dynamically constructing redirect URLs from request headers (`Origin` or `Referer`) could introduce an Open Redirect vulnerability if an attacker crafts an arbitrary `Origin` header.
* **Hardening:**
  1. Never reflect unvalidated headers.
  2. Extract the origin strictly using `new URL(rawHeader).origin` to eliminate paths, query strings, and port injections.
  3. Validate against a strict, tamper-proof whitelist:
     - Configured `process.env.CLIENT_URL`.
     - Static project aliases (`https://anime-alley-client.vercel.app`, `https://anime-alley-beige.vercel.app`).
     - Strict team-scoped preview regex: `/^https:\/\/anime-alley-client-[a-zA-Z0-9-]+-developers-projects-86df454e\.vercel\.app$/`.
     - Safe local development origins (`http://localhost:5173`, `http://localhost:3000`, `https://localhost:3000`).
  4. If validation fails or header is missing, hard-fallback to `process.env.CLIENT_URL || "http://localhost:5173"`. No dynamic strings are ever passed to Stripe without passing this validation.

### 2.2 Route Decoupling & Information Leakage Audit
* **Risk:** Moving `/verifyOrder` above `router.use(verifyTokenMiddleware)` makes it publicly reachable without a JWT.
* **Hardening:**
  1. **Zero Data Leakage:** `/verifyOrder` must ONLY return `{ success: true }` or `{ success: false }`. It must **never** return order items, user IDs, emails, prices, or shipping addresses.
  2. **Fail-Fast Parameter Validation:** In-memory validation enforces that `stripeSessionID` must be a non-empty string before acquiring a database connection (`await dbConnect()`).
  3. **High Entropy:** Stripe Checkout Session IDs (`cs_test_...` / `cs_live_...`) contain 256 bits of cryptographic entropy, making brute-force guessing mathematically infeasible.

### 2.3 Distributed Webhook Race Conditions
* **Risk:** In serverless architectures, the user's browser redirect from Stripe often completes in ~300ms, while Stripe's asynchronous webhook delivery may take 1–3 seconds to hit `/api/stripe/webhook` and record the order.
* **Hardening:**
  1. `Success.jsx` already implements polling (intervals of 2 seconds up to 10 attempts / 20 seconds).
  2. Add an unmount cleanup function `return () => clearInterval(timer)` to eliminate memory leaks.
  3. Implement a graceful timeout UI: If polling reaches the max attempt threshold without confirmation, do NOT display an error; display: *"Your order has been placed and is currently syncing. You will receive an email confirmation shortly."* with a direct action button to view `/history`.

### 2.4 Cancellation Flow
* **Risk:** If a user clicks "Back to Cart" within the Stripe Checkout interface, Stripe redirects them to `cancel_url`.
* **Hardening:** Both `success_url` and `cancel_url` must use the resolved dynamic origin so the user returns to the exact domain where their cart and session exist.

## 3. Detailed Technical Specification (File-by-File Changes)

### 3.1 `server/utils/origin.utils.js` [NEW]
Create a centralized, reusable origin validation utility to serve as the single source of truth for CORS and redirect services.

* **Purpose:** Ensure CORS middleware and Stripe redirect resolution use identical, strictly-verified origin rules.
* **Functions:**
  - `isOwnVercelOrigin(origin)`: Validates static domains and the verified team-scoped Vercel preview regex.
  - `resolveTrustedClientOrigin(req)`:
    - Extracts `req.headers?.origin || req.headers?.referer`.
    - Parses via `new URL(raw).origin`.
    - Returns the parsed origin if it matches `process.env.CLIENT_URL`, static domains, `isOwnVercelOrigin`, or `localhost`.
    - Returns fallback `process.env.CLIENT_URL || "http://localhost:5173"` on mismatch or error.
* **AGENTS.md Compliance:**
  - Single-line comments only (`//`).
  - Single-statement `if` blocks without curly braces.
  - Strict type checking on inputs.

```javascript
// Centralized origin validation utility for CORS and third-party redirect services
const dotenv = require("dotenv");
dotenv.config();

// Strict validator restricted strictly to your verified project and team scope on Vercel
const isOwnVercelOrigin = (origin) => {
  if (typeof origin !== "string") return false;

  // Specific known production domains registered to this project
  if (
    origin === "https://anime-alley-client.vercel.app" ||
    origin === "https://anime-alley-beige.vercel.app"
  )
    return true;

  // Strict regex for team-scoped preview deployments
  // Matches exclusively: https://anime-alley-client-<subdomain>-developers-projects-86df454e.vercel.app
  const teamScopedPattern =
    /^https:\/\/anime-alley-client-[a-zA-Z0-9-]+-developers-projects-86df454e\.vercel\.app$/;
  return teamScopedPattern.test(origin);
};

// Validates whether an origin is trusted for CORS and redirect operations
const isTrustedOrigin = (origin) => {
  if (!origin || typeof origin !== "string") return false;

  const configuredClientUrls = process.env.CLIENT_URL
    ? process.env.CLIENT_URL.split(",").map((url) => url.trim())
    : [];

  if (configuredClientUrls.includes(origin)) return true;
  if (isOwnVercelOrigin(origin)) return true;

  // Localhost development support
  if (
    origin === "http://localhost:5173" ||
    origin === "http://localhost:3000" ||
    origin === "https://localhost:3000"
  )
    return true;

  return false;
};

// Extracts and validates incoming request origin for safe redirect construction
const resolveTrustedClientOrigin = (req) => {
  const rawOrigin = req.headers?.origin || req.headers?.referer;
  if (!rawOrigin || typeof rawOrigin !== "string")
    return process.env.CLIENT_URL || "http://localhost:5173";

  try {
    const parsedOrigin = new URL(rawOrigin).origin;
    if (isTrustedOrigin(parsedOrigin))
      return parsedOrigin;
  } catch (e) {
    // Return safe default fallback on URL parse error
  }

  return process.env.CLIENT_URL || "http://localhost:5173";
};

module.exports = {
  isOwnVercelOrigin,
  isTrustedOrigin,
  resolveTrustedClientOrigin,
};
```

### 3.4 `server/routes/modules/order.route.js` [MODIFY]
* **Change:** Move `router.get("/verifyOrder", verifyOrder);` ABOVE `router.use(verifyTokenMiddleware);`.
* **Why:** Order verification relies exclusively on the cryptographically secure `stripeSessionID` and returns a simple `{ success: boolean }`. Decoupling it from the JWT middleware prevents false 401s during post-payment redirects and avoids triggering the frontend's `clearAllUserData()` interceptor.
* **Lines affected:**
```javascript
// Verify Stripe order completion (publicly accessible by high-entropy session ID)
router.get("/verifyOrder", verifyOrder);

// All subsequent order routes require authentication
router.use(verifyTokenMiddleware);

// POST
router.post("/placeOrder", placeOrder);
// GET
router.get("/getOrders", getOrderHistory);
router.get("/allOrdersList", requireAdmin, allOrdersList);
router.get("/orderStats", requireAdmin, getOrderStats);
// DELETE
router.delete("/delete/:orderId", requireAdmin, deleteOrder);
// UPDATE
router.put("/update/:orderId", requireAdmin, updateOrder);
```

### 3.5 `client/src/utils/userSessionManager.js` [MODIFY]
* **Change:** Fix the token key in `itemsToPreserve` from `"token"` to `"authToken"`.
* **Why:** The frontend application exclusively uses `"authToken"` in `localStorage`. If `clearUserData()` is called, having `"token"` in the preservation list causes `localStorage.removeItem("authToken")` to execute, accidentally logging out the user.
* **Lines affected:** Line 21:
```javascript
  // Items to preserve during user switch
  const itemsToPreserve = [
    "userInfo", // Keep new user info
    "authToken", // Keep authentication token
    "refreshToken", // Keep refresh token if exists
    USER_EMAIL_KEY, // Keep the new email reference
  ];
```
